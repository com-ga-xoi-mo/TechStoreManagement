# Design

## Context

- `DashboardPage` already uses C# Markup and implements `IRoutePage`. It binds to `DashboardViewModel` and has its own scroll region, three presets, and custom date fields in live mode. `DashboardViewModel` keeps `_appliedQuery`, uses `PageViewModel.RunLatestRequestAsync` for the Dashboard, and loads preview data through `IAnalyticsRepository`.
- `ShellViewModel` gets its menu and landing page from `RoleAccess`. `RoleAccess.CanOpen(AppRoute.Root(ShellDestination.Dashboard), role)` currently allows only Admin and Manager to open Overview. `ShellRoutePageFactory` checks access when creating the scope and lease. `ShellNavigationAdapter` replaces and disposes pages. The window switches between Shell and Login when the session generation changes.
- `AnalyticsApiRepository` already uses `IApiClient`, invariant query formatting, and DTO-to-model mapping. [Sales API change, D5](../archive/2026-11-25-m4-financial-report-sales-api/design.md#d5-dto-and-json-for-t-vinh) provides `FinancialReportDto` and the sample JSON. [Change 2, D5/D6](../archive/2026-11-25-m4-financial-report-refunds-restocks-warranty/design.md#d5-json-compatibility-aggregation-and-unknown-values) populates after-sales fields and adds a breakdown of refunded tax, cash and QR flows, and shifts. The sales sample represents the earlier response shape for compatibility tests.

## Goals / Non-Goals

**Goals** — Show figures for the correct period and session while preserving the meaning of each field. Support both desktop targets and allow repository and ViewModel tests without a UI thread.

**Non-Goals** — Shell menu, routes, landing page, or disposal changes. M3 Dashboard KPI, chart, query, preset, or preview changes. Financial calculations, exports, transaction drill-down, and changes to the API or shared DTOs.

## Decisions

### D1. Two views in one DashboardPage

- Put the tab selector at the top of `DashboardPage`, above both views. Use the localized labels “Tổng quan” (Overview) and “Báo cáo tài chính” (Financial Report). Set each accessible name (`AutomationProperties.Name`) to its visible label. Select exactly one tab at a time, indicate selection without relying on color, and expose the selected state to assistive technology. Select Overview by default on each activation. Keep the existing Overview UI tree in the page scope when switching views to preserve the M3 range, state, preview, chart, and independent requests. Load the report when the user selects its tab.
- Check authorization for tab visibility and before opening or loading the report. Use `ISessionStore.Current` to check for an Active session whose generation matches the activation, live mode, and the existing Dashboard rule in `RoleAccess`. The server authorizes requests through JWTs. Block opening the report and sending HTTP requests in preview, in anonymous or expired sessions, and for SalesStaff, WarehouseStaff, or unknown roles.
- Keep the Shell route, navigation item, title, menu, and landing page. If a new menu entry is needed later, update the design before implementation with minimal changes to the destination, route, page mapping, and guard, with confirmation from T. Vinh. The tab selector is local to the page and falls within Bình’s scope.

### D2. Repository and read contract

- Add the focused `IFinancialReportRepository` interface to the Analytics client. Extend `AnalyticsApiRepository` to read reports through `IApiClient` and register the live interface in the existing `DashboardAnalyticsServiceCollectionExtensions`. Preserve `IAnalyticsRepository` wiring and the M3 fixture. The Dashboard ViewModel receives the dedicated dependency in its current scope and calls it only after the D1 guard passes.
- Send `GET api/analytics/financial-report?period=custom&from=yyyy-MM-dd&to=yyyy-MM-dd` and pass cancellation to the transport. Use `FinancialReportDto` and the sales change D5 JSON as the baseline for existing fields and reuse the product and cashier row DTOs. The original shared DTO lacks the new fields. Use a typed Analytics client projection compatible with the earlier shape and read optional `refundTaxAmount`, `cashReceivedAmount`, `cashRefundPaidAmount`, `vietQrReceivedAmount`, `vietQrRefundPaidAmount`, and `cashByShift`. Map the projection to client models. Missing or `null` new fields remain unavailable. An absent shift array differs from an empty one. Keep the shared DTO and backend unchanged and deserialize into the client projection.
- Validate the response shape and metadata. Check the period, that the range matches the query, that `asOf` is valid UTC, that `timeZone=UTC+07:00`, that daily rows cover each date in order, and that the original arrays are valid. Declare or check the presence of required JSON fields in `summary` and every `daily[].totals`. For example, `salesExcludingTax` must contain a number, including zero, and `costOfGoodsSold` must be present but may be `null` when unavailable. Use `ApiErrorKind.InvalidResponse` when a required field is absent or a required non-nullable numeric field is `null`. Optional fields such as `refundTaxAmount` remain unavailable when omitted or `null`. Preserve decimal precision, nullable and negative amounts, and the server’s product and cashier order. Display totals as returned by the server.

### D3. Date range, state, and request lifecycle

- Keep draft dates in `dd/MM/yyyy` format, the immutable applied range, and the snapshot with its returned dates separately in the report ViewModel. Inject `TimeProvider`, use `TimeProvider.System` at runtime, and use a fixed clock in tests. Convert `GetUtcNow()` to UTC+07 to determine today on first opening the report in an activation and when validating the end date. The default range starts six days before today and includes today on the Vietnam calendar. Reuse `AnalyticsLimits.MaxCustomRangeDays`. Send a new range request only after a valid range is applied. Show draft errors on the corresponding fields and keep the current state and range. Refresh and Retry use the applied range even when the draft has changed.
- Keep report state in a headless child ViewModel of the Dashboard ViewModel. Track report work through `RunTrackedRequestAsync` so the lease waits for requests that ignore cancellation before disposing the scope. Give report requests their own cancellation token source and sequence number. The Dashboard keeps its own latest-request slot. Link the activation and window tokens. Let a valid Apply replace an in-flight request, cancel the prior token source, and keep it alive until the request exits. Selecting Overview cancels report work and clears its snapshot, while retaining the applied range within the same activation and session. Reopening the report fetches a fresh snapshot for that range.
- Capture the sequence, immutable range, and session generation when starting a request. Before publishing success, an error, or a loading-state change on completion, verify that these still match, the report is still open, and authorization remains valid. On a session change, cancel report work and clear report state, drafts, snapshots, and errors. The previous page must never issue a request under the new session. On deactivation, cancel and clear scope state and unsubscribe. Dispatch updates from background events to the activation’s UI context using the existing mechanism, keeping the logic testable without WinUI. Read the current generation before publication to reject stale results even when the UI callback is queued.
- Keep each range label paired with its own snapshot during loading. Publish the result and its label together only when they match the request. Expected cancellation is silent. For 400, timeout, network, 5xx, and malformed-response errors, show a Vietnamese message and allow retry while authorized. On 403, keep the session and show an access-denied message. The existing transport handles 401 for the correct generation through `BearerTokenHandler`. The report has no separate refresh-token logic or automatic replay.

### D4. Layout and field mapping

The top area contains the tabs, From (“Từ”) and To (“Đến”) dates, Apply (“Áp dụng”), Refresh (“Làm mới”), and the label “Kỳ … · Cập nhật … (UTC+07)”. Convert the UTC `asOf` to local report time and use it as the snapshot timestamp. Place errors and retry in the report panel. Group period totals into sales, cash flow, cost of goods sold, and after-sales sections. Show key figures in the daily table and provide keyboard-accessible detail by day so narrow windows do not need a 20-column table.

| Section | Display source |
| --- | --- |
| Sales, refunds, and tax | `salesExcludingTax`, `refundedSalesExcludingTax`, `netSalesExcludingTax`, `salesTax`, `refundTaxAmount`, `completedOrderCount`, and `quantity`. Show a legacy allocation warning when `allocationMismatchOrderCount` is nonzero and retain the reported amounts. |
| Cash flow | `paymentReceivedAmount`, `refundPaidAmount`, and cash and VietQR receipts and payouts when available. Use the API’s shift ID, receipts, payouts, and `cashNetMovement` for the period in `cashByShift`. Leave out synthetic names and inferred cash balances. |
| Costs, gross profit, and after-sales | `costOfGoodsSold`, `restockedCost`, `netCostOfGoodsSold`, `salesGrossProfit`, and `netGrossProfit`. Show `warrantyCost` separately as replacement device cost. |
| Daily figures | Use each `daily[].date` and the matching fields from `daily[].totals`, including zero-value days and unavailable amounts. |
| Products and cashier performance | Show `topProductsByQuantity`, `topProductsByRevenue`, and `cashierPerformance` in API order. Include names, quantity and sales, and available cashier metrics. The tables represent original sales rather than cash flows or net rankings. |

- Use declarative C# Markup bindings and commands. Apply `AppColors.Brushes` directly to elements so theme changes work while the report is open. Use `AppTypography/AppMetrics/AppControlStyles` for styling. Use color as a supplemental cue for labels, amounts, and focus. Keep UI control references out of the ViewModel and data synchronization out of view events. Any imperative focus when switching panels stays local to focus and lifecycle, with no data assignment. Test both targets.
- Format amounts with the `vi-VN` locale and `₫`, keeping negative signs and meaningful fractional digits at the VND precision in the contract. Display `null` as “Chưa tính được” and zero as “0 ₫”. Show a separate message for empty arrays. Because the API always returns a row per day and has no no-transaction flag, display “Không có số liệu phát sinh khác 0 trong kỳ” only when all relevant metrics are known and zero, and all lists are present and empty. Keep `asOf` and the zero-value daily table visible. If fields are missing, show known values. Individual zero or unavailable values do not establish an empty period.
- Set keyboard tab order through the selector, From, To, Apply, Refresh or Retry, and the content. Provide accessible names, visible focus, readable inline errors, and predictable focus on a panel switch or retry. Hidden content stays outside the tab order. At narrow widths, stack date controls and totals vertically, reflow daily details, and give wide tables local horizontal scrolling so all values remain accessible. Theme and size changes preserve focus and the applied range and send no request.

### D5. Verification by layer and platform

- Use the sales design D5 JSON as fixed headless test data. Verify October 12–14, 2024, `asOf=2024-10-15T02:00:00Z` displayed as 09:00 UTC+07, sales excluding tax of 480, tax of 36, receipts of 370, a zero-value day on October 13, unavailable costs and profit, and correct ranking order. Extend the fixture from change 2 D6 to verify negative amounts, refunded tax, warranty costs, cash and QR, shifts, and legacy JSON compatibility. Fixtures are for tests only.
- Verify live on PostgreSQL with an API build that includes change 2. Read the same range directly from the API and in the desktop app, compare daily and period totals, and verify authorization. Record limitations in the real source workflows, including end-to-end QR receipts if they remain unavailable. Distinguish a confirmed fixture from a verified real QR receipt flow.
- For each target, record the OS, target framework, client and API SHAs, run instructions, role, range, and results for Vietnamese and VND, keyboard and focus, resizing at 800×600, 1024×768, and 1440×1000 DIP, and switching light/dark themes with the report still open. Use the existing theme mechanism, or change the OS theme in System mode or through developer tools, to exercise the same view instance. Switching to Settings and reopening the report does not satisfy this check. For a native build failure, record “Not tested” with the command, error, and rerun conditions. Append all evidence to `docs/M4_FINANCIAL_REPORT.md` alone.

## Risks / Trade-offs

- The report contains many metrics. Group related figures and provide daily details to keep narrow windows readable.
- The two views load independently. Give each view its own request state, use the shared lease to await cleanup, and test with a fake that ignores cancellation.
- Clients may encounter an older API or incomplete sources. Keep the wire contract additive, label unavailable amounts, and identify the exact tested build in the verification document.

## Migration Plan

Integrate the client after the sales contract is available and verify it live after change 2. There is no data migration. To restore M3 Overview behavior, revert the selector, report panel, and report registration.
